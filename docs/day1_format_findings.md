**Consequence for the feature layer.** AEMO's pre-dispatch forecast is both a model
feature and the benchmark the project is measured against, so an as-of join keyed on
the generation timestamp would let the model read a forecast before it was published,
on exactly the comparison the project rests on. Join on `known_at`, which is the later
of the generation timestamp and the directory listing time.

One caveat worth recording rather than glossing: the directory index timestamp has
minute granularity and is assumed to be NEM time. It is an upper bound on availability,
not a measurement of it, which is the safe direction to be wrong in.

### Timestamp convention

- Filename label: `202608180100`
- First `SETTLEMENTDATE` in the file: `2026/08/18 01:00:00`
- File appeared on NEMWeb at: 2026-08-18 00:56:00 AEST

The file was listed -4 minutes relative to its own SETTLEMENTDATE.

The dispatch solve that produced it ran -4.8 minutes relative to the same SETTLEMENTDATE, at `00:55:12`.

**This settles the labelling.** The solve ran at the *start* of a five-minute interval and the row is stamped with the interval's *end*, so `SETTLEMENTDATE` is **interval-ending**.

It also explains why the file appears before the timestamp it carries, which looks wrong at first glance. A dispatch price is not measured after the fact — it is the output of a solve run at the start of the interval, which sets the price that interval will settle at. So the price for the interval ending 00:50 is determined at 00:45, published around 00:48, and applies to the five minutes that are still running.

**Consequence for the label, which is not covered by PLAN §4.1.** At prediction time `t` the price of the interval ending roughly `t+2` has already been published. A target defined as *any spike in `(t, t+30min]`* therefore includes one interval whose answer is already known. The target window must be defined over intervals whose DISPATCHIS was **not** published at or before `t`, and Day 4's leakage test must assert that as well as the feature-side condition.

### Intervention and price variants

`INTERVENTION` present, values in this file: `{'0': 5}`

When AEMO intervenes in the market it solves dispatch twice, once physically and once for pricing, and both solutions can appear for the same interval. Staging must filter to a single run rather than averaging them.

Price columns available: `RRP`, `ROP`, `RAISE6SECRRP`

`RRP` is the regional reference price used for settlement; `ROP` is the price originally produced by the solve before any intervention adjustment. The label must come from `RRP`.
