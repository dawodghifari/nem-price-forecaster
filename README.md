# NEM Price Spike Forecaster

![CI](https://github.com/dawodghifari/nem-price-forecaster/actions/workflows/ci.yml/badge.svg)

Forecasting the probability that the NSW spot electricity price exceeds
$300/MWh in the next 30 minutes, from AEMO's live five-minute dispatch feed,
measured against AEMO's own published pre-dispatch forecast.

**Status: Phase 1 complete.** Data flows from NEMWeb into Postgres, dbt builds a
point-in-time-correct feature table, a LightGBM model is backtested against three
baselines, and a FastAPI service returns a live prediction. Every number below
was produced by a script in this repository and is regenerated by
`make baselines` and `make train`.

## The result

The model does **not** significantly beat AEMO's pre-dispatch forecast. That is
the honest summary and it is worth stating first.

Pooled over 116 spike episodes across 39 days (683 positive rows in 99,704):

| | PR-AUC | 95% CI | precision@200 | episodes caught @200 |
|---|---|---|---|---|
| Model (+ AEMO feature) | 0.498 | 0.342–0.629 | 0.790 | 50 of 116 |
| Model (no AEMO feature) | 0.470 | 0.324–0.606 | 0.775 | 41 of 116 |
| Persistence | 0.399 | 0.274–0.514 | 0.575 | 25 of 116 |
| AEMO P5MIN | 0.356 | 0.219–0.483 | 0.605 | 31 of 116 |
| Climatology | 0.025 | 0.014–0.044 | 0.000 | 0 |
| Random *(control)* | 0.007 | 0.004–0.010 | 0.010 | 2 |
| Shuffled labels *(control)* | 0.007 | 0.004–0.013 | 0.000 | 0 |

The model leads on every metric, and the confidence intervals overlap from 0.342
to 0.483. On 116 episodes that difference cannot be certified, so it is not
claimed. What can be stated as a count rather than an estimate: given a budget of
200 alerts, the model flagged 50 of the 116 episodes and AEMO flagged 31.

Confidence intervals come from a blocked bootstrap resampling whole trading days.
Resampling rows would treat six overlapping views of one event as six
independent observations and produce intervals far too narrow.

### The harder half

Spike episodes run 3.3 five-minute intervals on average, so most positive rows
are *continuations* of a spike already in progress. Simply asking "has the price
been above $300 recently" scores 84× the base rate. A model can therefore post a
strong overall number having learned nothing but persistence.

The **onset slice** — rows where nothing in the trailing 30 minutes had exceeded
the threshold — was defined and committed before any model was trained, precisely
so it could not be chosen afterwards as a flattering cut. It holds 302 positives
in 55 episodes at a 0.31% base rate, against 0.69% overall.

| on onset rows only | PR-AUC | 95% CI | precision@100 | episodes caught @100 |
|---|---|---|---|---|
| Model (+ AEMO feature) | 0.108 | 0.065–0.185 | 0.280 | 12 of 55 |
| Model (no AEMO feature) | 0.100 | 0.061–0.171 | 0.180 | 7 of 55 |
| AEMO P5MIN | 0.090 | 0.048–0.166 | 0.250 | 8 of 55 |
| Persistence | 0.057 | 0.033–0.098 | 0.080 | 2 of 55 |

A draw. AEMO is sharper at its very top alerts (precision@50 of 0.380 against the
model's 0.300); the model covers more distinct events. Neither wins.

### Reading these numbers

**Perfect foresight only reaches episode recall 0.164 at 100 alerts.** Ranking by
how severe a spike will be concentrates alerts inside the worst few evenings, so
episode-recall figures should be read against that ceiling rather than against
1.0. It also explains why the model exceeds perfect foresight on episode recall
at 200 alerts — it spreads its alerts across more events rather than piling them
on the largest one.

**Precision@k breaks ties chronologically**, on the grounds that an operator works
an alert queue in the order it arrives. `docs/day5_baselines.md` reports the same
figures averaged over random tie-breaking alongside; where they diverge, the score
is too coarse to rank at that budget. AEMO's precision@50 is 0.800 chronological
against 0.690 expected, so the lower figure is the fair one.

**Every metric carries its denominator.** "PR-AUC 0.498 over 116 episodes" is a
defensible sentence; the number alone is not.

## Two findings that outrank the model

**Persistence beats AEMO's own published rule.** At the $300 decision an operator
reading pre-dispatch actually faces, persistence achieves 0.514 precision and
0.558 recall on 741 alerts; AEMO achieves 0.432 and 0.521 on 825. Fewer alerts,
better on both. Pre-dispatch assumes bids stay as submitted, so it under-predicts
spikes driven by rebidding — the gap is expected, but not usually this visible.

**Spikes do not concentrate in summer here, and the plan assumed they did.**

| | Aug–Dec 2025 | Jan–Aug 2026 |
|---|---|---|
| spiking days | 40 | 10 |

January 2026 — peak summer — had one spiking day. March, April and June had none.
This is a regime shift rather than a seasonal cycle, and it is the strongest
argument in the project for the drift monitoring planned in Phase 3. The original
plan's stated limitation was wrong, and correcting it mattered more than any
tuning.

## How it is built

| | |
|---|---|
| MMS flat-file parser | Reads the column set from each file's own `I` records rather than an assumed schema |
| Raw layer | Postgres, append-only, three vintage timestamps per row |
| Staging | Seven dbt models typing raw text, resolving vintages, deriving which days are complete |
| Features | One macro, two callers: a training mart requiring a complete outcome, a live mart for rows whose outcome has not happened |
| Evaluation | Episode-aware scoring written by hand — average precision, precision@k, episode recall, blocked bootstrap |
| Backtest | Expanding-window folds sized by spiking days, 24-hour purge gap, pooled scoring |
| Serving | FastAPI scoring a warehouse row, containerised |
| Tests | 187 Python (179 run offline; 7 need the populated warehouse, 1 needs MLflow), 69 dbt data tests |

### Point-in-time correctness

A pre-dispatch file's internal timestamp is not when it became readable: one run
generated at 23:35:33 did not appear on NEMWeb until 23:48. AEMO's forecast is
both a model feature and the benchmark, so joining on the internal timestamp
would let the model read a forecast twelve minutes before anyone could have.
Every raw row therefore carries `_generated_at`, `_listed_at` and
`_known_at = max(both)`, and only `_known_at` may be joined on.

Leakage has two sides, and the second is easy to miss. Features must not come
from the future, *and* the target must not already be known. AEMO publishes a
dispatch price about two minutes before the interval it belongs to ends, so a
target window defined on the clock always contains an interval whose answer is
already public — `tests/test_no_leakage.py` demonstrates that the naive window
leaks on every row. Predictions are anchored to publication events instead, which
also makes training and serving identical.

Both invariants are asserted three ways: as unit tests against planted leaks, as
dbt tests in the warehouse, and recomputed from the raw layer in Python by
`tests/test_leakage_against_raw.py`, which reuses none of the dbt SQL. Two
implementations agreeing is evidence; one agreeing with itself is not.

### What was deliberately not done

**No hyperparameter search.** Against 116 events, a search tunes to the fold
structure and the reported score stops being out-of-sample in the sense it
claims. Parameters were fixed before the first run. A better model probably
exists; this one's number is harder to attack.

**No class weighting.** `scale_pos_weight` on a 0.7% class distorts the output
probabilities, and the deliverable is an endpoint returning a probability
somebody acts on.

**Two models, not one.** AEMO's forecast is both a feature and the benchmark, so
it is run both ways: without it, the question is whether pre-dispatch can be
replaced; with it, whether it can be improved on.

### Controls

Every measurement runs alongside a floor and a ceiling. A random score must land
at the base rate; perfect foresight must reach precision 1.0; and a full backtest
on **shuffled labels** must also land at the base rate. That last one exercises
the entire training path — folds, purge, inner validation, prediction — against
data with no signal in it. It scored 0.007 against a base rate of 0.0069. The
scripts exit non-zero if any control misses.

## Running it

**Without the data:** `make test` runs the offline suite, 179 tests in about 20 seconds with no
database and no download. CI runs it on every push, alongside `ruff`, `dbt parse` and a build
of the API image.

**The full pipeline:**

```bash
cp .env.example .env
make up                # Postgres 16 + Adminer
make backfill          # ~13 months of NEMWeb archive, ~23 GB of downloads
make poll              # live 5-minute poller, leave running
make dbt-build         # staging, features, ~70 data tests
make baselines         # writes docs/day5_baselines.md
make train             # writes docs/day6_model.md
make fit               # persists the served model
make api && make smoke # live prediction from real data
```

`make smoke` is Phase 1's exit condition: `curl` returning a forecast from data
minutes old. `make refresh-serving` rebuilds the serving models in about four
seconds and belongs on the poller's cadence.

`data/` and `models/` are not committed. Both are reproducible.

## Limitations

**Thirteen months, one region, one summer.** The archive runs Aug 2025 – Aug 2026
for NSW1 only, and — as above — that summer was unusually quiet. The model is
fitted to a narrow slice of market conditions.

**116 episodes is not many.** It is enough to rank the baselines and not enough
to separate the top two. Wider confidence intervals are the honest consequence,
and they are reported rather than smoothed.

**The served model has no out-of-sample score of its own.** It is trained on all
available data, including the period the backtest evaluates. Its metadata says so
in words, and `/health` reports that note verbatim. The figures above describe
the *procedure*; they are not this artifact's performance.

**Feature importance says the model is largely a better persistence.** Recent
price accounts for 71% of total gain, `rrp_now` alone for 42%. AEMO's forecast
contributes 8.4% when available.

## Data

Market data © AEMO, used under AEMO's copyright permissions notice. Weather from
Open-Meteo, CC BY 4.0.

Weather uses Open-Meteo's **historical forecast** API with an explicitly named
model. Unspecified, that endpoint returns ERA5 reanalysis — data that did not
exist at prediction time — which would make every weather feature a leak. The
difference was measured, not assumed: unnamed returned 0.000 °C deviation from
ERA5, `ecmwf_ifs025` returned 0.586.
